# Local transcription and diarization, as a Provider

status: partially superseded by [ADR-0006](0006-zero-cloud.md) (2026-08-02) — the local pipeline this ADR introduced is now Braid's only pipeline; the Cloud/Local/Auto provider modes and fallback described below were removed with the cloud itself. The "developed for public use" premise below was also reversed: Braid is private and single-owner again (SPEC non-goal 7, [ADR-0007](0007-the-voice-database.md)).

[ADR-0002](0002-cloud-diarization-over-local.md) parked local ML for v1 and named the conditions for coming back; they arrived together. Braid is now developed for public use, and its README was turning away every machine with headroom for an on-device model — the exact people public source invites. FluidAudio, the project ADR-0002 evaluated, now ships batch pyannote community-1 diarization (10.6% DER on AMI SDM, 323x realtime) alongside Parakeet TDT v3, all CoreML on the Neural Engine under Apache 2.0. And the constraint that justified the prohibition turns out not to bind: the 8GB machine is strained *during* a Teams call, but Braid's pipeline is batch and every model runs after Stop, when the call app has released everything. R4's ≤5% CPU and ≤100MB budget covers the recording window, in which no inference happens. We therefore add a `LocalAdapter` behind the existing `STTProvider` seam, with two interchangeable engines — Parakeet TDT v3 by default, Apple's SpeechTranscriber selectable — and pyannote for the Remote Track. Transcription becomes Cloud, Local, or Auto; Auto prefers local and falls back to the cloud, always disclosing it.

ADR-0002's substantive objection — that aligning an unlabelled transcript against independent diarization segments is genuinely error-prone — is not dismissed, it is narrowed. Braid's split-file design means the Mic Track needs no diarization at all (it is one speaker structurally, ADR-0001) and only the Remote Track is ever aligned, containing nobody the user could be confused with. Both come off one aggregate device on one clock, so alignment is an overlap lookup rather than a search for the offset between two recordings. That reduction is what makes this safe now, and `SpeakerAligner` is a pure function tested without any model precisely because it is the part worth being sure about.

## Consequences

- **ADR-0004's zero-dependency policy now has exactly one exception**, taken deliberately: FluidAudio, pinned to an exact version. It is pre-1.0 and vendors a prebuilt binary xcframework plus two C/C++ targets, which is a real supply-chain cost in a publicly distributed app. It builds under Command Line Tools with no Xcode (verified), links statically, and needs no change to bundle assembly or signing. The exit is that the models are standard CoreML artifacts: replacing FluidAudio means writing a pipeline, not finding new weights. Any further dependency remains a decision to revisit ADR-0004, not a routine import.
- **ADR-0003 is unchanged and now has a place it could erode.** Diarization produces speaker embeddings, and `TimedSpeakerSegment` exposes the raw vector it clustered on. `LocalDiarizer` maps to `SpeakerSpan`, which has no embedding field and is the only way a result leaves that file, so voiceprints exist inside one call and are unreachable after it returns. FluidAudio's speaker-enrollment and speaker-database APIs are deliberately not linked. A test asserts nothing audio-derived reaches disk.
- **Local mode has no fallback Provider in its Environment at all.** Not a policy that could later be forgotten: with no cloud Adapter present there is nothing a failure can reach, so a Job parks for the user instead. Auto is the only mode that can send audio off the machine unasked, and it says so in the notification and in the Note's `provider` frontmatter.
- **The Provider seam paid for itself a second time.** The Job pipeline, merge rule, naming flow and Note format are untouched; the queue gained a fallback attempt and a conditional transcode, nothing more.
- **Cost accounting splits.** A local Session bills only the Claude summary. The AssemblyAI key becomes optional — setup outside Cloud mode is one key, not two.
- **Key Terms are weaker under Parakeet.** Apple's engine takes them as `contextualStrings`; Parakeet currently gets nothing, so the app's highest-leverage accuracy lever does not bias transcription in the default configuration. FluidAudio ships a custom-vocabulary rescorer that could close this, and wiring it is a measurement job of its own. Known regression, recorded rather than hidden.
- **Measured on real call audio 2026-08-02** (`fixture-remote.flac`, 246s, against the AssemblyAI reference for the same audio). Words are good: 9.6% WER for Parakeet, 10.3% for Apple, 100% coverage either way, at 64x and 43x realtime and under 320MB peak. **Attribution is not**: 61.4% and 70.5% turn purity, 23–27 utterances where the reference has 44. The diarizer finds 17 speaker changes where the reference alternates ~40 times, so short backchannels are absorbed into the surrounding speaker and attributed to the wrong person. The aligner is faithful to the spans it is given; the limit is the model's turn resolution. Lowering the 1.0s embedding floor to 0.4s and halving the segmentation step was tried: 62 turns but still 18 speaker changes, identical purity, 20% slower. Rejected. **That rejection was overturned on 2026-08-02 and is instructive about how it was wrong.** It was measured under Parakeet. Re-measured after Apple SpeechTranscriber became the default engine, the same settings take turn purity from 70.5% to 77.3% at no measurable time cost, because the finer turns are only worth having if the word timings are precise enough to place words inside them — Apple's are, Parakeet's were not. The tuning result belonged to the engine it was measured under, and nothing recorded that at the time. FluidAudio's `zeroVoteReembed`, which its own documentation describes as recovering exactly the turns this failure loses, was measured alongside and rejected on evidence: 68.2% purity and a third voice invented where the reference has two. This is a real regression against the cloud on the exact quality PROJECT.md's current theme is about, and it is why the default engine and Auto's preference are both open questions rather than settled ones.
- **Apple's word timings align better than Parakeet's.** With identical diarizer output, Apple scored 9 points higher on turn purity — its `audioTimeRange` run attributes are more precise than Parakeet's TDT token timings. Combined with zero download and Key Terms support, that is an argument for Apple as the default that did not exist when Parakeet was chosen.
- **Diarizer models load per Job rather than being cached.** `OfflineDiarizerManager` is non-Sendable, so holding one across an actor boundary is not expressible; building it per call also releases several hundred MB the moment a Job finishes, which on an 8GB machine is the better trade.
