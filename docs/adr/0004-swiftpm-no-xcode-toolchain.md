# SwiftPM + Command Line Tools, no Xcode, self-signed identity, zero dependencies

status: amended 2026-08-02 — the Anthropic `URLSession` call and the FLAC transcode below no longer exist ([ADR-0006](0006-zero-cloud.md), zero-cloud); the zero-dependency policy has exactly one deliberate exception, FluidAudio, pinned exactly ([ADR-0005](0005-local-transcription-as-a-provider.md)); the no-distribution reference below is SPEC non-goal 7 in the current numbering. The toolchain, signing identity, and everything else stand.

**Reversed, 2026-08-02.** Xcode 26.6 is installed and is the toolchain; MLX builds, and `scripts/build-app.sh` now runs `xcodebuild` because mlx-swift's own README is explicit that SwiftPM on the command line cannot compile Metal shaders — a `swift build` produces a binary that dies at the first MLX call with "Failed to load the default metallib". Two things survived the reversal and are worth keeping: `scripts/test.sh` still runs the unit tests under plain SwiftPM, because the test target does not depend on BraidMLX and so never needs Metal — the fast loop is unchanged at ~3 seconds. And installing Xcode *lowered* the available SDK, which is the opposite of the expectation: the App Store's newest Xcode carries the macOS 26.5 SDK while Command Line Tools had 27.0, so `LanguageModelError` vanished and the deployment target dropped to macOS 26.0. Braid uses nothing newer, so nothing was lost, but the lesson is that on a macOS still ahead of released Xcode, CLT is the more current toolchain.

**The reasoning, from when it was still pending:** The owner has chosen to install Xcode so MLX can be embedded, because Apple's on-device model refuses whole categories of legitimate recording ([ADR-0006](0006-zero-cloud.md)) and an open-weights model is the only fix that stays on the machine. That is the first thing Xcode buys that this project actually needs — the paragraph below, written when it bought nothing, is what changed. The consequences are accepted with it: a ~15GB toolchain, a second and third dependency exception (mlx-swift-examples and its tree), and Braid taking on multi-gigabyte model downloads. Nothing is wired until the toolchain can compile it; `Sources/BraidMLX/CUTOVER.md` holds the steps and the code, staged out of the build. The `@Generable` note below also stops applying once Xcode is present, though the hand-built schemas stay: they suit user-editable Presets better than a compile-time macro does.

**The toolchain choice has a cost, found by hitting it.** Swift macros load from compiler plugins, and Command Line Tools ships only three: Observation, SwiftMacros and Testing. Anything else is unavailable — including `@Generable`, the macro FoundationModels documents for guided generation. Braid builds its generation schemas by hand with `DynamicGenerationSchema` instead, which is the same feature at the cost of about forty lines. Worth knowing before reaching for a macro-based API: the question to ask is not "does the SDK have it" but "does its plugin ship with CLT". Swift Testing works because `scripts/test.sh` passes `-plugin-path` explicitly; a future macro would need the same, and would need its plugin to exist at all.

The build machine (macOS 27.0, Swift 6.4 CLT) has no Xcode, and installing it (12+ GB, App Store interaction) buys nothing the project needs. We build with Swift Package Manager: `swift build` produces the executable and a repo script assembles and signs the `.app` bundle (Info.plist, `LSUIElement`, resources). Signing uses a local self-signed identity, "ms-notes Development" (created 2026-07-31, trusted for code signing in the login keychain), which gives the stable code identity macOS's privacy system (TCC) needs to remember audio permissions across rebuilds — no Apple Developer account involved. Third-party dependencies are zero by policy: capture, CAF/FLAC audio, HTTP, Keychain, logging, and UI all come from OS frameworks, and the Anthropic call is plain `URLSession` HTTP.

## Consequences

- The bundle-assembly script is project-owned code (~50 lines) and is the only "build system" beyond SwiftPM; Xcode can still open the package later if GUI debugging is ever wanted.
- **SwiftUI is usable, but its state property wrappers are not.** The Command Line Tools ship only `libSwiftMacros` and `libObservationMacros`; there is no `SwiftUIMacros` plugin, so `@State` and friends fail to compile with "plugin for module 'SwiftUIMacros' not found". Views therefore hold no state of their own. Each one reads an `@Observable` model owned by the AppKit controller that presents it, and passes explicit `Binding(get:set:)` values down. Observation drives the redraws, so this costs nothing at runtime and keeps views as pure functions of a model. Adding `@State` anywhere means requiring Xcode, which is a decision to revisit this ADR.
- The self-signed identity exists only on this machine — reinstalling macOS or moving machines means re-creating it and re-granting permissions (acceptable: non-goal #6, no distribution).
- Adding any SPM dependency is a deliberate decision to revisit this ADR, not a routine import.
