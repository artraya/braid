# Personal Meeting-Notes Pipeline (ms-notes)
status: ready-for-spec
explored: 2026-07-30

## Kernel
A polished macOS menu-bar app that captures mic + system audio locally during any call (no bot participant), sends the recording to a cloud STT API with speaker diarization after the call, summarises with a separate LLM API call, writes markdown notes into the Obsidian vault automatically, and deletes the raw audio. The STT layer is a pluggable provider abstraction (user-selectable provider), and vault delivery is a plain markdown file write into the vault folder — no Obsidian plugin involved [opinion: user, confirmed 2026-07-30].

Interpretations set aside: "buy the outcome" (commercial tools) — rejected by the user, who wants control and automation, not another subscription [opinion: user]. "Teams-native transcription + Graph retrieval" — investigated and closed as primary path (see Evidence). Live/real-time summarisation — deferred as a future nice-to-have [opinion: user].

## Problem hypothesis
The user's meeting knowledge evaporates after calls; manual note-taking during calls is lossy and distracting [assumption, medium — self-reported, not measured]. Existing tools solve this only as commercial subscriptions with their own UIs, and none deliver notes into the user's Obsidian vault automatically [fact, high — landscape survey below]. Volume is light: ~2–5 hrs of calls/week [fact, high — user-stated]. Hardware constraint: the machine is an 8GB M3 MacBook Air already strained by Teams (especially during screen sharing), so the app must be near-zero-impact during calls — no local ML, no web-runtime shell [fact, high — user-stated 2026-07-30].

## Potential users
Single user: the builder. Personal tool; no market ambition stated [fact, high]. The popularity of Granola (bot-free macOS AI notes) and Anarlog (~8.9k stars) is evidence the underlying need is real and widespread [fact, high].

## Current alternatives
- **Granola** ($14–35/user/mo): proves the exact product shape (bot-free system-audio capture + LLM notes on macOS) but is a subscription with its own silo; no Obsidian vault delivery [fact, high].
- **MacWhisper** (€59 one-time): local Whisper + system-audio capture + diarization, but output is a transcript; structured notes and vault automation are exactly the gap [fact, high].
- **Humla** (michaelwilhelmsen/humla), MIT, Rust+Tauri 2 + Swift sidecars, ~174 stars, actively developed (commit within the hour of 2026-07-30): **the closest existing match to this idea.** Bot-free mic (`AVAudioEngine`) + system audio (`ScreenCaptureKit`) kept as separate streams; cloud STT selectable in `Settings → Transcription` (OpenAI incl. `gpt-4o-transcribe-diarize`, Deepgram Nova-3/2, Groq) with keys in the macOS Keychain and per-language overrides; BYO-LLM markdown summaries with presets; click-to-rename speakers applied transcript-wide; RAG chat over notes. **Gaps vs this idea:** no Obsidian integration and no configurable output folder — notes live in SQLite at `~/Library/Application Support/no.humla.app/`, so vault delivery needs a DB-reading bridge, not a folder setting; **diarization is on-device only by design** (FluidAudio/CoreML, Community-1 or Sortformer, "no audio uploaded") with no cloud option; Tauri WebView shell; ScreenCaptureKit rather than process taps (Screen Recording permission + purple indicator + monthly re-approval); providers exclude the accuracy leaders (ElevenLabs/AssemblyAI/Speechmatics); no calendar-roster naming. Repo README, retrieved 2026-07-30 [fact, high]. **User has run it and reports performance problems on the 8GB M3 Air** [fact, high — user-reported 2026-07-30], plausibly local Whisper (500MB–1.1GB model) plus the WebView shell rather than diarization (~30MB on the Neural Engine) [assumption, medium — untested].
- **Anarlog (ex-Hyprnote)**, MIT, active: bot-free mic+system capture in separate channels, BYO-LLM summaries, markdown export. Missing: turnkey cloud STT with diarization, Obsidian auto-delivery [fact, high]. Superseded by Humla as the closest match.
- **Meetily**: right capture architecture, but diarization and markdown export are gated behind a paid PRO tier; local-only STT [fact, high].
- **Teams native recording + Graph API**: transcripts arrive pre-diarized with real speaker names, APIs unmetered since Aug 2025 — but requires tenant admin consent even for delegated access, a mandatory recording banner, manual record-start, and covers Teams only [fact, high — MS Learn, 2025-12/2026-07].
- **Obsidian plugin route**: dead — Electron cannot obtain macOS loopback audio from plugin-land [fact, high].
- **Doing nothing**: free, but the problem persists; rejected by user appetite (chose "polished app from the start") [opinion: user].

## Contradictory evidence
- **Cloud diarization gives anonymous labels ("Speaker 1"), while Teams-native transcripts attribute real names.** On Teams calls the DIY pipeline is a regression on speaker naming unless names are mapped manually or via calendar/heuristics [fact, high].
- Silent bot-free recording of private conversations generally requires all-party consent in Australia (e.g. WA Surveillance Devices Act). Mitigation chosen: verbal mention + auto-delete raw audio after processing [fact, medium — jurisdiction-specific; opinion: user accepts with mitigation].
- The pipeline's differentiating component — diarization quality on real compressed Teams audio — has zero independent accuracy data (see Evidence). [fact, medium]
- In the rare phone-on-speaker case there is no system audio at all and mic-track bleed degrades separation; the pipeline must degrade gracefully to mic-only mode [fact, high].
- Anarlog already delivers most of the value (capture, notes, markdown) for zero build effort; the delta being built is the cloud-STT + diarization + vault automation layer [fact, high].
- The "no public API to query system-audio permission" gap means a denied permission yields silent recordings with no error — a nasty failure mode for a set-and-forget tool [fact, high].
- **A live transcript cannot reuse the batch accuracy leader.** ElevenLabs Scribe v2 has the best independent English WER (2.2%) but its realtime model offers neither live diarization nor multichannel, so a live feature requires a second provider (Speechmatics or AssemblyAI) — live pushes the design toward paying two providers, or accepting a lower-accuracy final transcript [fact, high].
- **Persistent voiceprints are a live legal risk, not a theoretical one.** Otter.ai is defending a consolidated class action (N.D. Cal., consolidated 2025-10-22) alleging it stored voiceprints during calls and used them to identify speakers in later meetings without consent — attacking the cross-meeting reuse specifically, not the recording or transcription. Under the Australian Privacy Act, biometric templates used for automated identification are "sensitive information" requiring consent, and biometrics sit in the OAIC's 2025–26 regulatory priorities [fact, high on the litigation; medium on the AU application — read via practitioner summaries]. Rules out cloud speaker-enrollment APIs.
- **No shipping product publishes speaker-naming accuracy**, and no benchmark exists for calendar-constrained LLM naming or for speaker verification on mixed-remote-channel VoIP audio (VoxCeleb error rates do not transfer). Credible, near-total absence of evidence — which itself suggests accuracy is not good enough to advertise [fact, high].

4. **Fork Humla** — better base than Anarlog (closer feature match, same license), but the two changes that matter most for this idea (native lightweight shell, file-based vault output) cut against its architecture rather than extending it.
5. **Non-build: Granola or MacWhisper** — set aside; fails the stated goals of control, no-subscription, and vault automation [opinion: user].

## Key risks
- **Feasibility:** diarization quality on the remote channel of compressed meeting audio is unverified for every provider (no independent DER); the whole notes-quality promise leans on it. Silent-failure permission model on macOS. Possible macOS 26 point-release audio regressions (precedent exists).
- **Desirability:** notes quality depends at least as much on the summarisation prompt/LLM as on WER; a great transcript with a mediocre summary still fails the user. [assumption, medium]
- **Viability:** consent posture relies on discipline (mentioning recording) rather than mechanism. Provider churn is fast (Slam-1 and LeMUR already deprecated within a year) — the STT layer must be swappable. [fact, high]
- **Timing:** none material.

## Recommended direction
**Superseded 2026-07-30 — now "investigate further" (one bounded test) rather than "proceed".** The discovery of Humla (see Current alternatives) introduces a credible non-build path that did not exist in the evidence base when the user chose to proceed. The single decisive experiment is whether Humla, with transcription switched to a cloud provider, is acceptable on the 8GB M3 Air during a Teams call. If it is, the fresh build must justify itself on the remaining deltas alone — vault-native file output, native lightweight shell, process-tap capture without Screen Recording permission, and access to the higher-accuracy providers — which is a much narrower case than before. If it is not, the fresh build is the answer and the earlier recommendation stands.

The prior recommendation, retained for the record:

**Proceed**, with one bounded validation step before any app code: a bake-off of ElevenLabs Scribe v2, AssemblyAI Universal-3.5 Pro, and Mistral Voxtral Transcribe 2 on one real recorded call (they have free credits/tiers), judging diarization usefulness and Australian-accent accuracy on the user's actual audio — the one thing no public benchmark answers.

Performance envelope (hard constraint from the 8GB M3 Air): native Swift/AppKit menu-bar app (`LSUIElement`, no Electron/Tauri); process-tap capture with on-the-fly AAC/FLAC encoding at 16kHz per channel (~15–30MB/hr, flat RAM) on `.utility` QoS so encoding lands on efficiency cores; event-driven mic-in-use detection (no polling, 0% idle CPU); upload deferred until the call app releases the mic. Expected in-call footprint ~1–3% CPU / ~40–60MB RAM [assumption, medium — derived from QuickRecorder/AudioCap behavior, to verify in build].

**V1 scope, decided by the user 2026-07-30 — deliberately minimal:** record mic + system audio as two tracks; send both to one cloud provider for transcription with diarization; support custom key terms; summarise with a separate LLM call; write markdown into the vault; delete the audio. **Auto-detection of call start is explicitly out of v1** (user, 2026-07-30) — start/stop is manual. Also in v1: **pause/resume recording**, **crash-resilient recording**, **explicit speaker-count hints**, **explicit English language setting**, and **built-in summary prompt presets** (meeting / lecture / interview / training session).

V1 feature notes, with the API specifics confirmed 2026-07-30:
- **Pause/resume**: mark the gap in the transcript (e.g. `[recording paused]`) rather than silently concatenating, so the summariser does not read two unrelated segments as continuous.
- **Crash resilience — format choice matters.** Do **not** encode AAC into an M4A/MP4 container: the index is written only on clean shutdown, so a crash yields an unplayable file. Use **CAF**, Apple's format designed for unknown-length recording that tolerates truncation. Combined with continuous flushing to disk, a crash costs seconds rather than the meeting. [fact, high — container behaviour is well established]
- **Speaker-count hints**: `speaker_labels: true` enables diarization. `speakers_expected` sets an exact count, but AssemblyAI's docs warn "providing an incorrect exact count can negatively affect diarization accuracy" and "may produce random splits of single-speaker segments or merge multiple speakers into one"; they recommend `speaker_options.min_speakers_expected` / `max_speakers_expected` as a range when uncertain. **The two-track design yields a free accuracy win: the mic track is known to contain exactly one speaker, so an exact hint of 1 is safe there.** Use a range on the remote track. Docs also recommend ≥30s of continuous speech per speaker for reliable labelling — brief interjections may not get their own label. [fact, high]
- **Language**: set `language_code` explicitly. **`en_au` exists as a distinct code** from `en` / `en_us` / `en_uk`, and Universal-3.5 Pro supports Australian English. Setting it also avoids a silent-failure mode: with automatic detection, "features that aren't supported for the detected language are silently omitted from the response" — diarization could vanish without an error. [fact, high]
- **Summary presets**: stored prompt templates (meeting, 1:1, lecture, interview, training session), receiving the speaker-labelled transcript.

Operational requirements surfaced 2026-07-30 (recommended for v1; user has not yet ruled on them):
- **Gate audio deletion on confirmed success.** Deleting after processing but before the note is verified written turns any transcription or LLM failure into permanent loss of the meeting. Retain failed recordings until resolved.
- **Persist the transcript, not only the summary.** Free to store, and allows re-summarising without paying to re-transcribe — which also de-risks iterating on the prompt presets.
- **Queue and retry uploads when offline.** Calls end without connectivity; a fire-and-forget upload turns that into a lost meeting.
- **Surface a running cost total.** Primarily to catch runaway retries or accidental re-processing early.
- **Store API keys in the macOS Keychain**, not a config file. **Live transcription and live diarization are dropped from v1** ("put on the back burner… we can develop it in the future or work on local models if we need to"). This removes streaming connections, the scrollback UI, and the second provider from scope, and narrows provider selection to batch capability only.

**Provider recommendation for v1: start with AssemblyAI Universal-3.5 Pro, add ElevenLabs Scribe v2 as the second adapter and compare on real audio.** Cost does not separate them — ~$11.60/mo (ElevenLabs: $0.22 + $0.05 keyterms, diarization included) vs ~$11.70/mo (AssemblyAI: $0.21 + $0.02 diarization + $0.05 keyterms) at ~43 billed hours. AssemblyAI first on documented-risk grounds: the multichannel/diarization incompatibility is explicitly stated so the split-file path is known up front (ElevenLabs leaves this undocumented), custom vocabulary is specified at up to 1,000 terms with a published price, $50 free credit covers the evaluation, and training opt-out is self-serve (ElevenLabs zero-retention is enterprise-only). **Counterpoint held open:** ElevenLabs is measurably more accurate — 2.2% vs 3.1% WER, ~30% fewer errors — which is why the second adapter is a v1 task, not a later one. [opinion: Claude, evidence-backed]

Live scrollback transcript (explored 2026-07-30; **deferred out of v1 by user decision** — retained here as research for a possible v2): technically feasible and performance-free (a WebSocket streaming 16kHz mono is lighter than the file encoding already happening; the popover costs nothing while closed), and cheap — ~$3–6/month more than batch-only at the user's volume. But it is architecturally consequential: it forces a second STT provider (the batch accuracy leader cannot stream with diarization), and live speaker labels retroactively rewrite themselves, so the UI must render a mutable transcript rather than an append-only feed. **The channel split degrades gracefully**: even with unstable remote diarization, "you vs them" is exact and stable from the two-track capture alone, which is sufficient for catching up after a break. Recommend shipping v1 with the batch pipeline and the pluggable provider layer that makes live a bounded addition later [opinion: Claude; user decision pending].

**Scope decision (user, 2026-07-30):** "recreate all of Humla (minus the interface)" as a menu-bar-only native app, plus two additions — **custom vocabulary / keyterm biasing** passed to the transcriber, and **speaker labels fed into the summarisation prompt**. Calendar-roster naming is explicitly **out of scope**; manual speaker naming is accepted. This removes EventKit, its permission, and the closed-set LLM inference from v1 entirely — a material simplification.

Diarization (user preference, 2026-07-30): **cloud does both transcription and diarization; no local diarization in v1.** Reasons, in order of weight: (1) the provider returns speaker labels already attached to words, eliminating the timestamp-merging step that local diarization would require between two separately-produced artifacts — the main source of fiddly correctness bugs; (2) less code and one fewer dependency — no bundled models, no Neural Engine work; (3) better accuracy than pyannote Community-1's 17% DER, at zero-to-trivial added cost. Local diarization via **FluidAudio** (pyannote Community-1 on the Apple Neural Engine, ~21MB, Apache-2.0, native Swift) is **parked, not rejected** — its LS-EEND streaming model remains the cheapest route to live diarization if the live transcript is ever pursued, because it avoids needing a streaming STT provider that supports diarization. Embedding pyannote.audio/PyTorch directly is rejected outright on the 8GB constraint. Note this does not remove per-provider submission differences (Deepgram takes both channels plus diarization in one request; AssemblyAI requires split-file submission) — absorbing those is the provider layer's job.

Speaker naming (explored 2026-07-30; **superseded for v1 by the manual-naming scope decision above** — retained as the design to reach for if manual labelling proves tedious): EventKit calendar attendees as a closed candidate set → expected-remote-speaker-count hint passed to the diarizer (free accuracy on the cluster layer) → a single closed-vocabulary LLM call that maps each cluster to one candidate name or "unknown" and **requires an evidence quote** to assign a name (this structurally eliminates naming absent third parties, naming people merely discussed, and fabrication) → one-tap correction persisted to a local person registry, retro-applicable to stored transcripts → recurring-event identity memory keyed on the calendar series, which auto-names standing 1:1s and weekly syncs with no voice analysis at all. **No voiceprints in v1**; if local-only embeddings are ever added they must stay on-device, off by default, and individually deletable, with the boundary between within-meeting clustering and persisted cross-meeting profiles treated as a deliberate architectural line [opinion: Claude, evidence-backed; user decision pending].

Preferred architecture direction (provisional, for spec to decide): fresh Swift menu-bar app using Core Audio process taps + one aggregate device, two-track recording, and a **pluggable STT provider layer** — each adapter converts provider output to a canonical transcript format (words, timestamps, speaker labels, channel), absorbing per-provider quirks (Deepgram: single-request multichannel + diarization; ElevenLabs/AssemblyAI: split-file submission with mic channel plain, remote channel diarized). Multi-provider support is justified by observed provider churn: AssemblyAI deprecated Slam-1 and LeMUR within a year; ElevenLabs re-priced Scribe 40% [fact, high]. Summarisation is a **separate LLM API call** (recommended: Claude Opus 5 via the Claude API, ~$0.08–0.12 per one-hour meeting at $5/$25 per MTok — ~$1–2/month at the user's volume [fact, high — current pricing, retrieved 2026-07-30]), not the STT provider's bundled summariser, to keep the note template fully controlled and both layers independently swappable. Vault delivery is an atomic markdown file write into the vault folder (filename + frontmatter template is a spec decision). Auto-detection via mic-in-use listener.

Evidence that would reverse this: bake-off shows all three providers' diarization is unusable on real Teams audio (→ pivot to hybrid: local capture for any-call coverage + Graph transcript ingestion for names on Teams calls); or process-tap capture proves broken on macOS 26 (→ re-evaluate ScreenCaptureKit despite its permission nags).
